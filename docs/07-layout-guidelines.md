# Универсальная инструкция для ИИ: архитектура React и стиль Tailwind

## 1. Цель и область применения

Создавай интерфейсы на React и TypeScript с секционной архитектурой и оформлением непосредственно в JSX через Tailwind. Сочетай стандартные utilities с точными значениями из дизайна. Делай компоненты понятными, состояние — локальным, структуру — соразмерной задаче.

Эта инструкция описывает подход к написанию кода. Она не задает предметную область, фреймворк маршрутизации, палитру, шрифт, библиотеки интеграций или способ развертывания.

В существующем проекте сначала изучи его соглашения. Сохраняй принятые решения, если задача не требует их изменения. В новом проекте используй предложенные ниже правила как исходную основу.

## 2. Что выяснить до начала работы

Перед изменениями прочитай конфигурацию проекта и несколько близких по назначению компонентов. Установи:

- Как организованы маршруты, страницы, общие оболочки и локальные компоненты.
- Какие компоненты интерфейса уже существуют и как устроены их props.
- Как подключены Tailwind, глобальные стили, шрифты и дизайн-токены.
- Какие единицы измерения, контейнеры и брейкпоинты используются.
- Как принято объединять условные классы и разрешать их конфликты.
- Где проходят серверные и клиентские границы, если они есть.
- Как организованы данные, формы, локализация и внешние интеграции.
- Какие команды форматирования, проверки типов, линтинга и сборки доступны.

Отделяй действующее соглашение от единичного примера. Наличие библиотеки в зависимостях или файла с утилитой еще не означает, что они используются во всем проекте.

## 3. Архитектура по ответственности

### Страница

Страница собирает экран из крупных смысловых блоков. На этом уровне удобно видеть порядок секций, общую композицию и связь с маршрутом.

```tsx
const OverviewPage = () => {
    return (
        <main>
            <IntroSection />
            <FeaturesSection />
            <DetailsSection />
            <ContactSection />
        </main>
    );
};

export default OverviewPage;
```

Получение данных и подготовка props могут находиться на уровне страницы, если это соответствует архитектуре приложения. Не превращай страницу в файл со всей разметкой, валидацией, обработчиками и деталями отдельных контролов.

### Секция

Секция отвечает за самостоятельный смысловой блок: его компоновку, оформление, внутреннее поведение и адаптивность.

Храни секции конкретной страницы рядом с ней. Выноси секцию в общую область, когда она действительно переиспользуется или имеет самостоятельный контракт.

Не дроби каждую оболочку и строку текста на отдельный компонент. Выделение оправдано, если оно дает понятную ответственность, переиспользование или заметно упрощает чтение.

### Общий UI-компонент

Общие компоненты описывают повторяемые элементы интерфейса: кнопку, поле, карточку, вкладки, диалог, accordion.

Они получают содержимое и состояние через типизированные props и по возможности не знают о конкретной странице, маршруте или бизнес-процессе.

### Общая оболочка

Оболочки отвечают за повторяемые части экрана: навигацию, шапку, подвал, боковую панель и общие providers.

Перед подключением оболочки проверь существующую композицию: один и тот же элемент не должен появляться одновременно в layout и внутри секции.

### Hooks и вспомогательные функции

Выноси повторяемую логику React в hooks, а независимые вычисления — в обычные функции. Локальные обработчики оставляй рядом с компонентом, пока у них нет отдельной ответственности или реального переиспользования.

Ниже приведен возможный способ размещения файлов. Названия каталогов иллюстративные; существующую структуру проекта не требуется приводить к этому дереву.

```text
src/
├── pages-or-routes/
│   └── overview/
│       ├── page.tsx
│       └── components/
├── components/
│   ├── ui/
│   ├── layout/
│   └── providers/
├── hooks/
├── lib/
├── assets/
└── styles/
```

Не добавляй архитектурные слои ради самого разделения на слои. Развивай структуру по мере появления новых обязанностей и связей.

## 4. Серверные и клиентские границы

Если фреймворк поддерживает серверные компоненты, отделяй подготовку данных от интерактивности по правилам этого фреймворка.

Состояние интерфейса, эффекты и работа с браузерными API требуют соответствующей клиентской границы. Не обращайся к `window`, `document` или браузерному хранилищу в контексте, где они недоступны.

Для изменения размеров, отступов и видимости предпочитай CSS. Используй JavaScript для адаптивности, когда от размера экрана действительно зависит поведение или вычисление.

Сохраняй принятый способ рендеринга и развертывания. Изменение интерфейса само по себе не должно неявно требовать нового серверного окружения.

## 5. Основной стиль Tailwind

### Оформление рядом с разметкой

Записывай обычное оформление непосредственно в `className`:

```tsx
<section className="relative w-full py-12 md:py-20">
    <div className="mx-auto flex w-full max-w-6xl flex-col gap-6 px-6 md:gap-10">
        {children}
    </div>
</section>
```

Значения и брейкпоинты в примерах иллюстрируют синтаксис. Выбирай их по дизайну и настройкам проекта.

Длинная строка utilities допустима. Не переноси оформление в отдельный CSS-класс только ради сокращения строки JSX. Повторяющуюся самостоятельную структуру обычно лучше выразить компонентом.

Глобальные стили используй для глобальных правил: базовых переменных, шрифтов, поведения документа и общих системных настроек. Для локального элемента предпочитай локальное оформление.

### Стандартная шкала и точные значения

Используй стандартные utilities, когда они соответствуют нужному результату:

```text
flex items-center gap-4 p-6 rounded-xl text-base font-medium w-full
```

Используй arbitrary values для значений, которые действительно требуют точности:

```text
max-w-[42.5rem]
gap-[1.125rem]
rounded-[1.25rem]
text-[2.75rem]
leading-[0.95]
tracking-[-0.04em]
```

Не округляй точную геометрию произвольно. Не создавай arbitrary value для значения, которое уже удобно выражается существующей шкалой или токеном.

Повторяющиеся значения сначала сверяй с принятой темой. Если новое значение становится общим правилом нескольких компонентов, рассмотри токен в рамках существующей системы.

## 6. Единицы измерения и контейнеры

### Сначала выясни размер rem

`rem` зависит от вычисленного `font-size` корневого элемента. Не считай его автоматически равным фиксированному числу пикселей.

Возможны разные системы:

- Постоянный базовый размер шрифта.
- Адаптивный размер через media queries.
- Масштабирование через `vw`.
- Ограниченное масштабирование через `clamp()`.

Используй систему, которая принята в проекте. Не вводи масштабирование через `vw` только ради повторения этого руководства.

Если нужно перевести размер из макета:

```text
размер в rem = размер в CSS-пикселях / вычисленный размер 1rem
```

При адаптивном корневом размере учитывай ширину окна, для которой сделан макет. Не меняй глобальный размер шрифта ради подгонки одного блока.

### Выбирай единицы по назначению

| Единица | Когда уместна |
| --- | --- |
| `rem` | Типографика, отступы, размеры в общей шкале |
| `em` | Размеры относительно шрифта элемента, трекинг |
| `%` | Относительные размеры и смещения |
| `px` | Тонкие границы и детали с фиксированной толщиной |
| `vw`, `vh` и их варианты | Размеры относительно viewport при явной необходимости |

Не смешивай единицы случайно. Проверяй результат при изменении ширины окна и масштаба браузера.

### Разделяй фон и ширину содержимого

Внешняя оболочка может занимать всю ширину, а внутренняя — ограничивать контент и задавать боковые отступы.

Используй существующий контейнер проекта. Не предполагай, что класс `container` имеет стандартное поведение: проверь глобальные определения, ширину, `max-width`, padding и возможный `!important`.

Изменяй геометрию отдельной секции через ее внутренние оболочки. Общий контейнер меняй только при задаче на всю систему компоновки.

## 7. Адаптивность

Пиши базовое оформление для узкого экрана, затем добавляй изменения на нужных брейкпоинтах:

```tsx
<div className="flex flex-col items-stretch gap-6 md:flex-row md:items-start md:gap-10">
    {children}
</div>
```

Выбирай брейкпоинты из конфигурации и фактического поведения контента. Не добавляй все доступные префиксы на каждый элемент.

Типичные изменения:

- Вертикальная компоновка становится горизонтальной.
- Меняется число колонок.
- Меняются выравнивание, интервалы и размеры текста.
- Второстепенные элементы скрываются или перемещаются.
- Навигация переключается на компактный вариант.

Сохраняй одну разметку, если меняется только оформление. Отдельные мобильную и настольную структуры используй, когда существенно отличаются композиция или взаимодействие.

Если в DOM остаются обе версии, учитывай повторяющиеся `id`, состояние форм и выполнение эффектов: CSS-скрытие не размонтирует компонент.

Для JS-зависимого поведения согласуй порог с CSS и очищай подписки в эффектах. Не создавай JS-состояние ширины окна ради свойства, которое решается responsive utility.

## 8. Типографика, цвета и визуальная композиция

### Типографика

Сначала определи иерархию: главный заголовок, заголовки секций, основной текст, подписи, вспомогательные данные. Для каждого уровня согласуй размер, насыщенность, высоту строки и трекинг.

Точные значения line-height и letter-spacing допустимы, если они нужны дизайну. Плотные строки и отрицательный трекинг подходят не любому шрифту и тексту: проверяй читаемость и отсутствие обрезания.

Выбирай семантический тег по смыслу, а визуальный стиль — через классы. Размер текста не определяет уровень заголовка.

Принудительные переносы используй только для управляемой композиции. Проверяй их на разных ширинах и языках, если приложение локализовано.

### Цвета

Используй существующую палитру и токены. Если проект оформляет точные цвета через arbitrary values, следуй этой практике в локальных изменениях. Не вводи новую палитру без задачи на дизайн.

Различай прозрачность элемента и прозрачность цвета: `opacity-*` влияет на весь элемент вместе с потомками, а прозрачность цвета текста или фона — на соответствующее свойство.

### Сложная композиция

Используй обычный поток, flex и grid для основной структуры. Абсолютное позиционирование и отрицательные отступы подходят для декоративных элементов и намеренных наложений.

Не строй всю страницу из абсолютных координат, если содержимое может меняться. Проверяй композицию на длинном тексте и промежуточных ширинах.

## 9. Условные классы и варианты

Для небольших условий используй принятый в проекте способ: шаблонную строку, `clsx` или существующий helper.

```tsx
className={clsx(
    'rounded-xl border p-6 transition-colors',
    isActive ? 'border-current opacity-100' : 'border-transparent opacity-70',
)}
```

Пример предполагает наличие `clsx`. Не устанавливай отдельную библиотеку ради одного простого условия.

Передавай полные имена классов. Не собирай Tailwind-классы из фрагментов динамических значений:

```tsx
// Нежелательно: имя класса получается только во время выполнения.
const className = `grid-cols-${columns}`;

// Для конечного набора вариантов используй полные строки.
const columnsClass = {
    single: 'grid-cols-1',
    double: 'grid-cols-2',
};
```

Для непрерывных вычисляемых значений используй `style` или CSS-переменные по соглашениям проекта.

`clsx` объединяет строки, но не разрешает конфликты Tailwind. Внешний `className` последним аргументом не гарантирует, что соответствующее CSS-свойство победит.

Если компонент должен поддерживать переопределение utilities, используй существующий механизм объединения конфликтующих классов либо проектируй явные props для поддерживаемых вариантов. Не создавай несколько утилит с одинаковым назначением.

Применяй `!important` точечно после выяснения причины конфликта. Не используй его как стандартную основу оформления.

## 10. Изображения, иконки и сложные эффекты

Перед созданием нового изображения или иконки проверь существующие assets и библиотеку компонентов.

- Контентным изображениям задавай содержательный `alt`; декоративным — пустой `alt`, если они представлены тегом изображения.
- Декоративный фон размещай на подходящей оболочке, учитывая позиционирование, масштабирование и повторение.
- Используй принятый в проекте компонент изображения и корректные пути к ресурсам.
- Проверяй API конкретной иконки: поддерживаемые props могут различаться.
- Для управления внешним видом вложенных элементов используй локальные варианты `group`, `peer` или селекторы, когда это делает связь понятнее.

Если несколько utilities записывают одно CSS-свойство, проверь итоговый результат. Например, градиент и фоновое изображение могут оба задавать `background-image`. Для нескольких слоев нужна одна согласованная многослойная запись.

Inline style уместен для вычисляемой геометрии, transform, CSS-переменных и сложного эффекта, который неудобно выражать utilities. Простые постоянные отступы и цвета оставляй в Tailwind.

## 11. Анимации и состояния

Используй CSS transitions для простых hover-, focus- и open-состояний. Выбирай анимируемое свойство явно, когда это возможно.

```text
transition-transform duration-300 ease-in-out hover:scale-[1.015]
```

Это пример мягкого hover-эффекта, а не обязательная анимация всех интерактивных элементов. Длительность и амплитуду выбирай по дизайну.

Библиотеку анимаций используй для поведения, которое оправдывает ее сложность: координации состояний, жестов, входа и выхода элементов.

Продумывай не только hover, но и focus, active, disabled, loading, error, empty и success, если они применимы к компоненту. Учитывай предпочтение уменьшенного движения.

## 12. React, TypeScript и состояние

Используй функциональные компоненты и явные типы props. Следуй принятому в проекте выбору между `type` и `interface`, именованным и default export.

- Имена компонентов пиши в PascalCase.
- Соглашение об именах файлов бери из окружающего кода.
- Размещай состояние как можно ближе к месту использования.
- Поднимай состояние, когда им действительно должны управлять несколько компонентов.
- Используй стабильные ключи в списках.
- Очищай слушатели, таймеры и другие подписки в эффектах.
- Не добавляй мемоизацию без понятной причины.
- Не применяй `any` или подавление ошибок типов как стандартный способ завершить реализацию.

Для оберток над нативными контролами сохраняй нужные нативные props, обработчики и доступ к DOM по принятому в проекте способу. Явно определяй, какому элементу принадлежат `className`, props контейнера и ref.

Не вводи глобальное хранилище ради состояния одной секции. Повторяемую бизнес-логику отделяй от JSX, когда это упрощает ее использование и проверку.

## 13. Данные, формы и локализация

Используй существующий способ получения данных. Наличие библиотеки запросов не означает, что каждый локальный список нужно переводить на сетевой запрос.

Для формы определяй:

1. Тип и начальное состояние данных.
2. Правила валидации.
3. Ошибки конкретных полей и общие ошибки отправки.
4. Состояние отправки и защиту от повторного действия.
5. Поведение после успеха.
6. Доступные подписи, подсказки и сообщения.

Переиспользуй существующие поля и поток отправки. Не копируй конфигурацию внешнего сервиса или предметные правила из несвязанной формы.

Если приложение локализовано, добавляй новые тексты во все поддерживаемые словари и сохраняй принятые правила внутренних ссылок. Не предполагай конкретный набор языков или структуру URL.

Обычный текст выводи через JSX. HTML-строки используй только при обоснованной необходимости и с учетом доверия к источнику.

## 14. Форматирование и читаемость

Источником истины служат настройки форматтера и линтера проекта. Не навязывай собственные отступы, кавычки, порядок импортов или завершающие запятые.

Если подключен плагин сортировки Tailwind, доверяй ему порядок utilities. Не поддерживай параллельно собственный ручной порядок.

В условном `className` отделяй постоянную основу от состояний и внешних расширений. Крупные JSX-блоки группируй по смыслу; комментариями объясняй причины и ограничения, которые неочевидны из кода.

Форматируй измененные файлы. Не переформатируй несвязанные части проекта в рамках локальной задачи.

## 15. Что сохранять и что не копировать

Сохраняй устойчивые соглашения: размещение компонентов, модель состояния, систему размеров, палитру, типографику, адаптивность и инструменты проекта.

Не превращай случайные недостатки в стандарт:

- Пустые атрибуты и неиспользуемые импорты.
- Закомментированные старые реализации.
- Дублированные стили и обработчики.
- Конфликтующие utilities без ясной цели.
- Массовое использование `!important`.
- Динамическую сборку имен Tailwind-классов из фрагментов.
- Проверки маршрутов, не учитывающие реальную структуру URL.
- Лишние клиентские границы.
- Отсутствие семантики, подписей и доступного управления с клавиатуры.

Исправляй такие недостатки в пределах задачи. Более широкую реорганизацию проводи, когда она необходима для результата или отдельно запрошена.

## 16. Порядок работы ИИ

1. Прочитай инструкции репозитория, конфигурацию стилей и ближайшие аналоги.
2. Установи устойчивые соглашения и отдельно отметь исключения.
3. Определи минимальное место изменения в архитектуре.
4. Найди существующие компоненты, assets, токены и интеграции.
5. Раздели страницу на смысловые секции, затем определи общие элементы.
6. Реализуй базовую компоновку и адаптивные изменения.
7. Добавь состояния и поведение, сохраняя локальную ответственность.
8. Проверь доступность, длинное содержимое и пограничные состояния.
9. Отформатируй изменения и запусти подходящие проверки проекта.
10. Просмотри diff на случайные правки и необоснованное усложнение.
11. Сообщи, что изменено, что проверено и какие ограничения остались.

### Проверка результата

Выбирай проверки по характеру изменения:

| Изменение | Что проверить |
| --- | --- |
| Верстка | Узкие, широкие и промежуточные экраны; переполнение; переносы |
| Адаптивность | Обе стороны используемых брейкпоинтов |
| Общий компонент | Существующие места использования и поддерживаемые состояния |
| Форма | Валидация, отправка, повторное действие, ошибка, успех |
| Навигация | Реальные URL, активные состояния, клавиатура |
| Локализованный блок | Поддерживаемые языки и различия длины текста |
| Логика | Релевантные сценарии и существующие тесты |

Используй настроенные команды проекта для типов, линтинга и сборки. Не считай успешную сборку доказательством того, что отдельные проверки тоже выполнялись.

Не создавай тестовую инфраструктуру ради простой визуальной правки. Добавляй тесты, когда они проверяют значимое поведение и соразмерны риску изменения.

Отделяй чтение исходников от фактической проверки в браузере. Не заявляй о визуальной корректности, если интерфейс не открывался.

## 17. Готовая инструкция для передачи ИИ

```text
Работай в секционном стиле React и Tailwind, сохраняя соглашения проекта.

Сначала изучи конфигурацию, глобальные стили, общую оболочку и несколько
близких компонентов. Не принимай единичное решение за правило всего кода.

Страница собирает смысловые секции. Локальные секции храни рядом со
страницей, переиспользуемые UI-компоненты — в общей области.
Состояние держи рядом с использованием. Новые слои и зависимости добавляй
по необходимости, сохраняя принятые серверные и клиентские границы.

Оформление записывай непосредственно в JSX через Tailwind.
Сочетай стандартные utilities с точными arbitrary values по дизайну.
Используй существующие токены, палитру, шрифты, контейнеры и assets.
Перед выбором rem проверь размер корневого шрифта.
Не меняй глобальную систему размеров ради отдельного блока.

Начинай с узкого экрана, затем добавляй responsive utilities по реальным
потребностям контента и настройкам проекта. Одну структуру адаптируй CSS;
раздельные версии создавай при существенных различиях композиции.
Не используй JS для изменений, которые достаточно выразить CSS.

Для условных классов используй принятый helper или шаблонные строки.
Записывай полные имена Tailwind-классов. Вычисляемые значения передавай
через style или CSS-переменные. Учитывай конфликты utilities;
порядок аргументов объединения строк не гарантирует переопределения CSS.

Переиспользуй существующие контролы, формы, запросы и локализацию.
Продумай состояния взаимодействия, семантику и управление с клавиатуры.
Не копируй дублирование, лишние зависимости и случайные ошибки старого кода.

Следуй форматтеру и линтеру проекта. Сделай минимальное законченное
изменение, проверь релевантные сценарии и адаптивность, просмотри diff.
Сообщи о выполненных проверках и оставшихся ограничениях.
```
